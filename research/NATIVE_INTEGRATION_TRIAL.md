# Goal Devin — Native Integration Trial

## Purpose

This document replaces the superseded `goal-devin ultra --script` trial. It
proposes the smallest possible implementation slice that closes the live Devin
integration gaps identified in Phase R0.5:

- Authenticated launch of the genuine native Devin TUI.
- Exact model selection passed through to `devin`.
- A separate, read-only sidecar process that observes Goal Devin-owned state.
- One temporary custom subagent profile generated by Goal Devin.
- One observation-only hook event received from `devin`.
- Clean sidecar termination and cleanup of Goal Devin-owned temp files.

The trial intentionally does **not** include the full goal-loop rewrite,
arbitrary workflow scripts, parallel independent sessions, rate-limit auto-retry,
a complete dashboard, a Rust rewrite, PTY interception, keyboard injection, or
screen scraping.

## Black-box acceptance contract

The trial is considered successful if:

1. `goal-devin start` (or equivalent command) launches `devin` with the user's
   terminal attached and with the exact `--model` the user selected.
2. While `devin` is running, a Goal Devin sidecar process observes at least one
   `PreToolUse` or `PostToolUse` hook event and records the sanitized tool name
   and session id.
3. Goal Devin creates exactly one temporary custom subagent profile under
   `.devin/agents/goal-devin-<nonce>/AGENT.md` before `devin` starts and cleans it
   up after `devin` exits.
4. When `devin` exits, Goal Devin prints a short summary: session id, model,
   permission mode, and the list of observed tool names.
5. Existing `goal`/`resume`/`status`/`logs` commands continue to work unchanged.
6. No Goal Devin-owned temporary files remain after exit, except logs under
   `~/.goal-devin/`.
7. All existing tests still pass and `ruff` is clean.

## Candidate A — Python

### Files

| File | Purpose |
|------|---------|
| `src/goal_devin/launcher.py` | `Launcher` class: build argv, set env, spawn `devin` attached to the user's terminal, wait for it to exit. |
| `src/goal_devin/sidecar.py` | `Sidecar` class: run a read-only subprocess that writes a temp `devin` config with a `PostToolUse` hook, observes hook events, and streams sanitized records to a local socket/file. |
| `src/goal_devin/profile.py` | `CustomProfile` context manager: writes a temporary `.devin/agents/goal-devin-<nonce>/AGENT.md` with a pinned model and removes it on exit. |
| `src/goal_devin/cli.py` | Add `start` subcommand and route to `Launcher`. |

### Approach

- `Launcher` uses `os.execvp` or `subprocess.run` to run `devin` directly with
  stdin/stdout/stderr connected to the user's terminal. Goal Devin becomes a
  thin launcher, matching the finding that the native TUI must own the terminal.
- `Sidecar` runs in a separate process. It creates a temp HOME with a
  `devin` config that points `PostToolUse` at a tiny Python hook script. The
  script appends sanitized JSON to a file in `.research-evidence/` or
  `~/.goal-devin/observations/`. The sidecar exits cleanly when `devin` exits.
- `CustomProfile` writes an `AGENT.md` with frontmatter `model: <user-model>`
  so the trial exercises the custom subagent machinery.

### Pros

- Uses the existing Python test harness, fake `devin` fixture, and `GoalLoop`.
- Fastest path to a working end-to-end trial.
- Easy to iterate and measure.

### Cons

- Requires Python in the user's environment (already required by `goal-devin`).
- Less portable as a single static binary if distribution becomes a goal later.

## Candidate B — Rust

### Files

| File | Purpose |
|------|---------|
| `crates/goal_devin_launcher/` or `src/main.rs` | `Launcher` that spawns `devin` with the user's TTY as stdin/stdout/stderr. |
| `src/sidecar.rs` | Read-only sidecar that writes a temp `devin` config, installs a hook, and reads sanitized hook records. |
| `src/profile.rs` | Temporary `AGENT.md` writer/cleaner. |
| `src/cli.rs` | `start` subcommand and argv builder. |

### Approach

- Same black-box behavior as Candidate A, but implemented in Rust.
- Use `tokio`/`std::process` to spawn `devin` and wait.
- The sidecar can be a Rust async task or a separate Rust binary; the hook
  logger can be a small Rust script or a Python script invoked by `devin`.

### Pros

- Self-contained static binary, no Python dependency for the launcher.
- Easier to reason about long-running process lifetimes and signal handling.

### Cons

- Requires building the Rust project, dependency resolution, and a new test
  harness.
- Re-implements the `GoalLoop`/worktree/state layer from scratch, which is
  out of scope for the trial.

## Decision rule

Run **Candidate A (Python)** first because the existing Python implementation is
the behavioral oracle. If the Python trial succeeds, use it to validate the
black-box contract. Candidate B (Rust) should only be attempted if:

- Distribution as a single binary is explicitly required, or
- The Python trial reveals that Python cannot reliably spawn `devin` and
  observe hooks simultaneously.

**The final language decision is deferred until this trial completes.** No major
new workflow feature or Rust rewrite should be built before the trial.

## Out of scope

- Changing the existing `goal`/`resume`/`status`/`logs` implementation.
- Implementing a workflow scripting DSL (`goal-devin ultra --script`).
- Spawning parallel independent `devin -p` sessions as the primary fan-out.
- Auto-retry on rate limits.
- A full dashboard or native TUI reimplementation.
- PTY interception, keyboard injection, or screen scraping.

## Verification plan

1. Run `uv run pytest tests/ -v`.
2. Run `uv run ruff check . && uv run ruff format --check .`.
3. Run `goal-devin start --model swe-1-7` in a canary repo and inspect the
   terminal-owned `devin` session.
4. Verify the sidecar captured at least one `PostToolUse` event.
5. Verify the custom profile directory was removed.
6. Verify `goal-devin status` and `goal-devin logs` still work.
